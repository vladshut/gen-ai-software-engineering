Banking Transaction
Pipeline

A four-agent deterministic system that validates, scores fraud, screens compliance, and settles transactions — exposed as a configurable REST API chain with a file-based audit trail.

Created by  Vladyslav Shut
Overview

What the system does

  • Loads raw transactions from sample-transactions.json.
  • Validates structure, amount (Decimal > 0, ≤ 2 dp), and ISO-4217 currency.
  • Scores fraud with a fixed additive model → decision band.
  • Screens compliance — sanctions list + restricted jurisdictions.
  • Settles approved/review (FX → USD + 0.1% fee), holds flagged, rejects the rest.
  • Writes a final record per transaction and asserts a known outcome oracle.

Agent 1

Transaction Validator

  • Enforces required fields, amount, and currency contract.
  • Amount must parse as Decimal > 0 with ≤ 2 decimal places.
  • Currency must be in the accepted ISO-4217 set.
  • Rejections carry a rejection_reason.
  • If rejected → chain stops immediately.

Rejects

  • TXN006 — currency XYZ
  • TXN007 — negative amount
  • missing fields, > 2 dp

Agent 3 · New

Compliance Checker

  • Sanctions screening — destination account checked against a frozen sanctioned set.
  • Restricted jurisdictions — metadata.country checked against blocked countries (KP, IR, SY).
  • Already-rejected transactions pass through untouched.
  • If either check fires → status = "rejected" with reason.
  • Chain stops immediately on rejection.

Catches in sample data

  • TXN003 → rejected
    sanctioned destination: ACC-9999
  • TXN004 → rejected
    restricted jurisdiction: IR
Agent 4

Settlement Processor

  • approved / review → settled: FX-convert to USD, apply 0.1% fee.
  • flagged_review → held (not settled).
  • rejected → stays rejected.
  • Records fx_rate, amount_usd, fee_usd, net_usd.
  • Terminal step — always writes the final record.

Money handling

  • All amounts are decimal.Decimal — never floats.
  • Fees use ROUND_HALF_UP, min $0.01.
  • Static, documented FX rates to a USD base.

Chain behaviour

  • /pipeline calls step 0
  • Each step calls the next via HTTP
  • Rejection → chain stops, result written
  • Settlement always writes final record
Configurable

Pipeline step config

PIPELINE_STEPS = [ {"name": "validator", "path": "/steps/validator"}, {"name": "fraud", "path": "/steps/fraud"}, {"name": "compliance", "path": "/steps/compliance"}, {"name": "settlement", "path": "/steps/settlement"}, ]
  • Step order is a single list in api_server.py.
  • To reorder or add steps — edit the list.
  • Settlement must remain the terminal step.
  • GET /config returns the current order at runtime.
  • Each step is independent — easy to add new agents.

Design decision

Why deterministic agents — no LLMs

The rules are fixed and known. An LLM would be slower, costlier, and unauditable — for zero gain.

  • Correctness — exact, reproducible; makes the oracle meaningful.
  • Auditability — every decision is traceable on paper.
  • Cost & latency — a rule check is free and instant.
  • Scale — high volume is an infrastructure problem, not an intelligence one.
